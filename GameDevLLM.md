# GameDev Text LLM Project Plan

Ниже — последовательный план и артефакты для обучаемой текстовой LLM, которая помогает создавать игры (концепты, механики, уровни, контент, опционально код) и поддерживает консольные команды. Все пояснения написаны по-человечески.

## 0. Изначальная база знаний (создана первой)
- **Где лежит:** `knowledge_base.jsonl` — 61 стартовая запись (design, mechanic, level, content, code, qa) по разным жанрам и стадиям. Формат строки: `{ "type":..., "stage":..., "input":..., "output":..., "tags":[...] }`.
- **Зачем:** даёт модели начальные примеры ответов для Unreal/русского контента; служит bootstrap-корпусом перед сбором новых итераций.
- **Как применять:**
  - при генерации ответов — подмешивать примеры из близких тегов (genre/engine/difficulty);
  - при дообучении — использовать как ранний SFT-батч; новые /patch добавляются как новые строки без удаления старых;
  - при анализе качества — сверять ответы с похожими образцами из БД.
- **Правила обновления:** любая правка пользователя записывается новой строкой с `spec_delta`/контекстом; старое не удаляется, устаревшее помечается тегом `deprecated` или `superseded_by:<id>`.

## 1. Цель и границы модели
- **Что решает:** генерация игровых идей, механик, уровней, контента, чернового кода (Unreal C++/Blueprint-псевдокод), правок и патчей по текстовым командам. Работает как чат/консоль.
- **Что не решает:** не компилирует проект, не билдит ассеты, не гарантирует баланс. Код — черновик, может требовать ручной доработки.
- **Примеры входов/выходов:**
  - Вход: описание жанра и сцены + команда `/stage prototype /engine ue5 /genre immersive sim`.
  - Выход: структурированный ответ (JSON спецификация, объяснение, лог для датасета, пользовательские предпочтения).

## 2. Базовая модель и токенизатор
- Требование: не менять токенизатор и словарь, только LoRA/PEFT. Понимание всех слов даёт сама база и её родной токенизатор; дообучение не ухудшает покрытие.
- Кандидаты:
  1) **Mistral 7B Instruct v0.3** (Apache 2.0, 7B, хорош на английском, средне на русском, умеет код).
  2) **Gemma 2B/7B IT** (Gemma 2.0, коммерчески дружественная лицензия, умеренный русский, хорошая эффективность на 12–16 GB VRAM).
  3) **LLaMA 3.1 8B Instruct** (кондициональная лицензия, сильный англ/код, русский терпимый, 16 GB VRAM желательно).
- Выбор под вводные (больше русский, один GPU RTX 3060 Ti 8 GB, без ограничений по контенту): **Gemma 2B IT** — компактная, помещается в 8 GB с LoRA, даёт приемлемый русский и код. Токенизатор используем без изменений.

## 3. Архитектура системы
- **База:** Gemma 2B IT + неизменный токенизатор.
- **Адаптация:** LoRA/PEFT для SFT; сохранение/загрузка отдельных адаптеров.
- **Режимы:**
  - Designer — фокус на концепте, механиках, уровнях, нарративе.
  - Coder — фокус на кодовых заготовках, псевдо-Blueprint, C++ фрагментах.
- **Команды (/stage, /engine, /genre, /constraints, /patch):** задают контекст и метаданные для лога и датасета.
- **JSON-спека (контракт ответа):**
  - `game_spec` — JSON с жанром, движком, core loop, уровни, контент, optional код-блоки.
  - `explanation` — человеческое пояснение решений.
  - `dataset_log` — объект с `input`, `output`, `stage`, `engine`, `genre`, `quality_tags`, `timestamp`.
  - `user_prefs` — обновляемые предпочтения (стиль, язык, запреты, любимые приёмы).
- **Стиль ответов по умолчанию:** без экономии текста; даём развёрнутые описания, числа, формулы и конкретные шаги даже если запрос короткий.
- **Логирование итераций:** каждая сессия сохраняет `train.jsonl` (примеры для SFT) и `user_prefs.jsonl`.

## 4. Формат датасета
- `train.jsonl` — строки вида `{ "input": ..., "output": ..., "stage": "prototype", "engine": "ue5", "genre": ["immersive sim"], "quality_tags": ["structured", "ru"], "timestamp": "ISO8601" }`.
- `user_prefs.jsonl` — агрегированные предпочтения пользователя со штампами.
- **Авто-валидация JSON:** проверка обязательных полей, типы (строки/массивы), валидность ISO8601 времени.
- **Примеры строк (синтетика):**
  1) `{"input":"/stage prototype /engine ue5 /genre immersive sim Сделай стелс-коридор.","output":"{...GameSpec...}","stage":"prototype","engine":"ue5","genre":["immersive sim"],"quality_tags":["ru","designer"],"timestamp":"2024-07-01T12:00:00Z"}`
  2) `{"input":"/stage graybox /engine ue5 /genre soulslike Добавь ловушку и чекпойнт.","output":"{...GameSpec...}","stage":"graybox","engine":"ue5","genre":["soulslike"],"quality_tags":["ru","coder"],"timestamp":"2024-07-01T12:05:00Z"}`
  3) `{"input":"/patch Ускорь перекат и усили урон огнём.","output":"{...PatchSpec...}","stage":"polish","engine":"ue5","genre":["soulslike"],"quality_tags":["ru","patch"],"timestamp":"2024-07-01T12:10:00Z"}`

## 5. Bootstrap-датасет
- Источники: синтетика "prompt → spec → code → fix"; ручные примеры пользователя; открытые тексты с совместимой лицензией (Apache/MIT/CC-BY) без копирования закрытых ассетов.
- Лицензии: сохраняем лицензии ссылкой в метаданных; фильтрация токсичного/PII по простой эвристике (регекс email/phone, мат — опционально пропускаем по запросу).
- Дедупликация: хеширование `input+output`; отсев повторов.

## 6. Код подготовки датасета (Python)
Скрипт `prepare_dataset.py` читает сырые JSON/текст, нормализует, валидирует и пишет `train.jsonl` и `user_prefs.jsonl`.

## 7. Код обучения SFT + LoRA
Скрипт `train_lora.py` (Transformers + PEFT): загрузка базовой Gemma 2B IT, её токенизатора без изменений, токенизация, обучение LoRA, сохранение адаптера.

## 8. Код инференса: текстовая модель принимает запросы
Скрипт `infer_cli.py`: REPL, парсинг команд, маршрутизация Designer/Coder, вывод 4 блоками (GameSpec JSON, Explanation, DatasetLog, UserPrefs), авто-сохранение итераций в датасет.

## 9. Eval/метрики
- Валидация JSON (формат ответа, обязательные ключи).
- Юнит-тесты на парсер и формат (при код-режиме — линтер кода блоков не обязателен, но можно).
- Эвристики играбельности: наличие core loop, целей, риска/награды.
- Human-in-the-loop: быстрая разметка "уд/неуд" + правки → пополнение датасета.

## 10. План итеративного улучшения
- Сбор правок после каждой сессии, дообучение раз в 1–2 дня батчами (LoRA).
- Критерии выпуска: стабильная валидация JSON (>99%), субъективная оценка качества концептов, время ответа в пределах 2–5 с на 3060 Ti.
- Хранить версии адаптеров с семантическими тэгами (v0.1-design, v0.2-coder...).

## 11. Модуль: Собственная модель с нуля
Ниже — полный пайплайн создания собственной текстовой модели под геймдев, с двумя вариантами мощности.

### 11.1 Варианты мощности
- **Вариант A (реалистичный под одну RTX 3060 Ti 8 GB):** ~350M параметров, 16 слоёв, hidden size 1024, 16 attention heads, RoPE, контекст 2K. Обучается за разумное время на 1 GPU с градиентным аккумулятором.
- **Вариант B (идеальный, но дорогой):** ~7B параметров, 32 слоёв, hidden size 4096, 32 heads, RoPE, контекст 4K. Нужны 8×A100 80 GB или эквивалент, десятки миллиардов токенов.

### 11.2 Токенизация
- **Алгоритм:** SentencePiece Unigram — устойчив к смешанному русскому/английскому и коду.
- **Размер словаря:** 32k для варианта A (держим компактно), 64k для варианта B (лучшее покрытие редких токенов и кода). Добавляем byte_fallback, чтобы любые символы кодировались без ошибок.
- **Как покрыть русский и код:** кормим смесью русскоязычных текстов, документации по движкам, кода C++/Blueprint-псевдо, англ. туториалов. В Unigram оставляем `character_coverage=0.9995`, чтобы кириллица не вылетала.
- **Код обучения токенизатора:** скрипт `train_tokenizer.py` учит SentencePiece Unigram на папке текстов, сохраняет `tokenizer.model` + `tokenizer.json` (совместимый с Transformers).

### 11.3 Архитектура модели
- **Общее:** автогенеративная causal LM (GPT-style), Rotary Positional Embeddings (RoPE), SwiGLU FFN, RMSNorm, дропаут 0.1.
- **Вариант A:** 16 слоёв, hidden 1024, FFN 2730, 16 heads, контекст 2048, параметры ~350M. Подходит для быстрых итераций, инференс <6 GB VRAM с 4-бит квантом.
- **Вариант B:** 32 слоёв, hidden 4096, FFN 11008, 32 heads, контекст 4096, параметры ~7B. Требует многогпу, зато покрытие языка ближе к ChatGPT.

### 11.4 Данные для pretraining
- **Общий текст:** русские и англ. новости, вики, книги с лицензиями CC-BY/CC-BY-SA/MIT, тех. блоги (без закрытых данных).
- **Геймдев-корпус:** статьи об игровом дизайне (вики, GDC открытые), открытые GDD на GitHub, README и исходники open-source игр (MIT/Apache/GPL), обсуждения механик на открытых форумах, диалоги разработчиков с публичных issue. Исключаем приватные ассеты.
- **Объём токенов:**
  - Вариант A: 15–25B токенов достаточно, чтобы база языка не рассыпалась и хватило знаний по геймдеву.
  - Вариант B: 200–400B токенов для покрытия на уровне ChatGPT-подобных моделей.
- **Фильтры:** удаляем PII (регексы по email/телефону), дубликаты по MinHash/SimHash, убираем нелегальные/закрытые материалы.

### 11.5 Pretraining
- **Objective:** causal language modeling (next-token), без маскированки.
- **Batch/seq_len/lr:**
  - Вариант A: seq_len=2048, global batch 512–1024 токенов (через grad accumulation), lr 2e-4 с cosine decay, warmup 2%, AdamW (β1=0.9, β2=0.95), weight decay 0.1.
  - Вариант B: seq_len=4096, global batch 2k–4k токенов, lr 1.5e-4, остальное аналогично.
- **Бюджет GPU-часов (оценка):**
  - Вариант A: ~350M params на 20B токенов ≈ 400–600 GPU-часов на 1×A100 40 GB; на 3060 Ti с 8-bit оптимизатором — недели, поэтому лучше арендовать облако 1–2×A100.
  - Вариант B: 7B на 300B токенов — десятки тысяч GPU-часов на 8×A100 80 GB; это стратегический проект.
- **Чекпоинты и валидация:** сохранять каждые 10k–20k шагов; валидация perplexity на держ-ауте (1–2% данных), плюс спец-тесты по геймдев-текстам.

### 11.6 SFT/LoRA после pretraining
- Берём готовый чекпоинт (A или B), добавляем LoRA (r=16, α=32, target_modules=[q_proj,k_proj,v_proj,o_proj]).
- Датасет: `knowledge_base.jsonl` + свежие сессии (`train.jsonl`). Seq_len 2048, lr 1e-4, epochs 3–5 для A; для B — 1–2 эпохи на большом батче.
- Скрипт `sft_train.py` делает это на PEFT, в адекватных дефолтах.

### 11.7 Инференс
- Скрипт `infer_cli.py` грузит локальную модель (`--model_dir`) и токенизатор (`--tokenizer`) из обученных артефактов, поддерживает LoRA адаптер (`--lora_dir`), маршрутизирует Designer/Coder и пишет логи в `sessions/`.
- Контекст 2K (A) или 4K (B); можно подать —max_new_tokens 512 по умолчанию.

### 11.8 Eval
- **Perplexity** на общем корпусе (держ-аут).
- **Спец-бенчмарк GameDev:**
  - JSON-валидность ответов (контракт 4 блоков).
  - Качество дизайна: наличие core loop, целей, рисков/наград, счётного баланса.
  - Код: сборка/линт простых C++/Blueprint фрагментов (компиляция тестовых сниппетов).
- **Human-in-the-loop:** разработчик ставит метки "годно/не годно" + правки; новые строки добавляются в `train.jsonl` и переобучаются LoRA раз в 1–2 дня.

## 12. Модуль: «Долго, но верно» — интернет + связи

### 12.1 Архитектура чтения интернета (внешний слой)
- **Поиск:** гибридный — BM25 (ключевые слова через SerpAPI/DuckDuckGo) + векторный (эмбеддинги MiniLM). Скрипт `search_web.py` делает поисковый запрос, забирает топ-N ссылок и текст страниц.
- **Отбор:** простые фильтры по доменам (приоритет: unrealengine.com, gdcvault открытые статьи, геймдев-блоги MIT/CC-BY). Если источник слабый или пустой — пишем в выводе "не нашла".
- **RAG:** `chunk_and_embed.py` режет тексты, строит эмбеддинги; `rag_answer.py` подбирает релевантные куски и вставляет их в контекст перед генерацией. Модель получает свежие знания без переобучения: поиск + контекстные вставки.

### 12.2 Архитектура понятных связей
- **Извлечение сущностей/отношений:** `build_graph.py` берёт чанки, выделяет ключевые термины (механики, движки, параметры, названия игр) и строит грубые триплеты ("похоже на", "использует", "зависит от" и т.д.).
- **Knowledge Graph / Memory Graph:** хранится как `graph.jsonl` с триплетами `(head, relation, tail, source_url, source_chunk)`. Не перезаписываем — только дополняем, старые данные остаются. При ответе граф даёт быстрые связи, RAG даёт цитаты.

### 12.3 Режим «долго, но верно» (slow-thinking pipeline)
1) План поиска (2–3 уточнённых запроса).
2) Два-три захода в веб-поиск; если результаты слабые, уточняем запрос по ключевым словам.
3) Суммаризация найденного по топ-чанкам (SourcesSummary) + фиксация источников.
4) Построение связей: выделяем термины, строим список связей/мини-граф (ConceptLinks), отмечаем согласие/споры по источникам.
5) Только после этого генерируем итог (FinalAnswer) + стандартные блоки GameSpec/DatasetLog/UserPrefs. Запрещено давать итог до выполнения пунктов 3–4.

### 12.4 Формат вывода (встроено в infer_cli.py)
- **SourcesSummary** — короткое резюме топ-источников.
- **ConceptLinks** — связи между терминами (список словесных ребер).
- **FinalAnswer** — человеческое резюме.
- Далее стандартные блоки: `GameSpec JSON`, `Explanation`, `DatasetLog`, `UserPrefs` (датасет-лог сохраняет источники и связи).

### 12.5 Минимальный MVP-код
- `search_web.py` — поиск + скачивание страниц.
- `chunk_and_embed.py` — разбиение и эмбеддинги.
- `build_graph.py` — извлечение триплетов, запись в граф.
- `rag_answer.py` — slow-thinking (план → поиск → summary → links → answer-шаблон).
- `infer_cli.py` — чат, который вызывает slow pipeline и печатает SourcesSummary/ConceptLinks/FinalAnswer + базовые блоки.

### 12.6 Проверка верности
- Модель опирается только на найденные фрагменты: SourcesSummary/ConceptLinks выводятся явно и логируются.
- Если нет релевантных источников, финальный ответ обязан сообщить: "не нашла надёжные источники".
- Эвристика доверия: приоритезируем домены из allowlist, помечаем ошибки скачивания `[fetch_failed:...]`.
- Логирование ошибок: каждый run записывает `search_results.jsonl`, `index/chunks.jsonl`, `graph.jsonl`; пустые/слабые результаты — сигнал для доработки запросов или ручного патча.
